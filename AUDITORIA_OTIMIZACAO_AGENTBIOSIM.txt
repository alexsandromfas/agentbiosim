Resumo executivo
----------------
A simulacao esta pesada no motor, nao apenas na renderizacao. O benchmark
headless com o substrato real rodou 2.0 s logicos a 60 FPS em 11.902 s de
wall time, com 1020 agentes. Isso significa que, nesse cenario, o core da
simulacao ja esta muito abaixo de tempo real antes de desenhar qualquer coisa.

O maior gargalo atual e a visao/sensoriamento. No substrato real:
- agents_update: 8.7886 s
- agent_sensor: 7.1317 s
- spatial_hash: 1.1141 s
- collision: 0.9190 s
- interaction: 0.8419 s
- agent_brain_forward: 0.7165 s

Leitura pratica:
1. A renderizacao pode estar travando a interface, mas o motor tambem esta caro.
2. Otimizar renderizacao ajuda a fluidez visual, mas nao resolve sozinho.
3. Antes de criar um sistema de visao mais sofisticado, e melhor atacar a
   arquitetura atual da visao, porque ela ja consome a maior parte do tempo.

Diagnostico por area

P0 - [NAO FEITO NESTE LOTE] Medir renderizacao separada da simulacao
Status: ainda pendente; o render recebeu culling, mas falta profiler visual separado.

Hoje os benchmarks medem bem o core headless, mas ainda falta uma medicao clara
de renderizacao. A UI usa Pygame dentro da janela PyQt. O loop faz:
1. processa eventos
2. engine.step(real_dt)
3. engine.render(...)
4. pygame.display.flip()

Como step e render rodam no mesmo loop visual, se qualquer um dos dois ficar
caro a janela parece travar. Precisamos medir separadamente:
- tempo de engine.step
- tempo de engine.render
- tempo de pygame.display.flip
- tempo segurando state_lock
- FPS visual real versus tempo simulado por segundo real

Otimizar sem essa medicao ainda e possivel, mas fica menos preciso.

Acao recomendada:
- Criar benchmark visual/offscreen ou profiler de UI opcional.
- Adicionar secoes de profiler: render_total, render_food, render_agents,
  render_obstacles, render_overlay, display_flip.
- Nao deixar esse profiler ligado por padrao.

Risco para a simulacao: nenhum se for apenas medicao.


P0 - [PARCIAL FEITO/TESTADO] Visao/sensoriamento e o gargalo principal
Status: backend Numba exato para retina single/fullbody implementado e testado; ainda falta reduzir alocacao/copia e migrar mais estado para arrays persistentes.

O caminho atual em sim/sensors.py usa batch_retina_sense, mas o "batch" ainda
processa cada agente individualmente. Para cada agente:
- consulta spatial_hash com query_ball
- filtra candidatos por tipo
- cria arrays numpy novos para candidatos locais
- calcula distancias e angulos
- no modo fullbody, cria matrizes raio x objeto para intersecao exata

Isso preserva uma visao mais correta, mas cria muitas alocacoes pequenas e
muita computacao por agente. No substrato real, com 1000 bacterias, retina 18,
visao 180 e fullbody, esse custo domina.

Otimizações seguras, sem mudar a regra biologica:
- Evitar recriar arrays pequenos por agente; usar buffers reutilizaveis.
- Criar buckets por tipo no spatial hash para nao filtrar food/bacteria/predator
  via list comprehension em todo agente.
- Trocar query_ball por uma API que preenche uma lista/buffer reutilizavel, para
  reduzir set/list temporarios.
- [FEITO/TESTADO] Migrar a intersecao fullbody exata para Numba ou outro kernel compilado.
- [PARCIAL FEITO/TESTADO] Separar backend de visao: fallback Python/NumPy antigo
  continua existindo; falta transformar em classes formais VisionBackend.
  A saida deve ser comparada contra o backend atual dentro de tolerancia.
- Precomputar configuracao de sensores por especie e so atualizar quando a UI
  mudar algum parametro, nao em todo agente/todo frame.

O que nao recomendo fazer agora sem decisao explicita:
- Aumentar retina_skip automaticamente.
- Reduzir retina_count.
- Trocar fullbody por single.
- Usar campo de densidade aproximado.

Essas alternativas podem acelerar muito, mas alteram a percepcao dos agentes.
Devem ser modos opcionais, nao substituicao silenciosa.


P0 - [PARCIAL FEITO/TESTADO] Renderizacao provavelmente amplifica o travamento
Status: culling visual implementado; falta medir render/flip separadamente.

Mesmo que o core ja esteja lento, a renderizacao pode piorar muito:
- EllipseRenderer cria Surface nova e faz rotate para cada agente por frame.
- Vision rays podem desenhar 18 linhas por agente.
- Overlay renderiza texto todo frame.
- Render percorre todas as comidas, agentes e obstaculos, mesmo fora da camera.

Otimizações seguras:
- Ativar renderizacao simples automaticamente quando populacao passar de um
  limiar configuravel.
- Culling visual: desenhar somente objetos dentro da area visivel da camera.
- Atualizar overlay textual a cada N frames, nao todo frame.
- Separar FPS visual do tick de simulacao: se a simulacao estiver cara, renderizar
  menos frames, mas continuar a simular de modo controlado.
- Nunca desenhar visao de todos os agentes por padrao em populacoes grandes.
- Desenhar visao apenas do agente selecionado ou de uma amostra.

Risco para a simulacao: nenhum, porque afeta apenas visualizacao.
Risco visual: o usuario pode ver menos detalhes quando modo performance estiver
ativo. Precisa ser claro na UI.


P1 - [PARCIAL FEITO/TESTADO] Spatial hash esta sendo reconstruido demais
Status: queries com buffer foram feitas; rebuild incremental continua pendente.

No benchmark real:
- 120 steps
- 277 rebuilds de spatial hash

O motor atual reconstrói/limpa/reinsere objetos mais de uma vez por step em
varios cenarios:
- antes dos sensores
- depois do movimento
- depois de alteracoes topologicas

Isso custa menos que a visao, mas tambem alimenta o custo da visao.

Otimizações seguras:
- Spatial hash incremental: cada objeto guarda suas celulas atuais; se ele
  mudou de celula, remove das antigas e insere nas novas.
- Separar hash de comida e hash de agentes. Comida muda menos que agentes.
- Buckets por tipo: food, bacteria, predator.
- API sem set temporario para consultas onde duplicata nao e problema ou onde
  o chamador consegue deduplicar melhor.
- Estatisticas de ocupacao para ajustar cell_size.

Risco:
- Alto se for feito de uma vez. Spatial hash errado quebra visao, comida,
  predacao e colisao.

Como validar:
- Testes de equivalencia query_ball antes/depois.
- Teste circular/retangular.
- Benchmark com contagem de spatial_hash_sample_misses = 0.
- Comparar eventos biologicos com seed fixa.


P1 - [PARCIAL FEITO/TESTADO] Parametros dinamicos geram overhead desnecessario
Status: sensores agora resolvem configuracao por especie/lote; config_dirty global ainda pendente.

Sensores e agentes consultam muitos params.get em loops quentes. Isso e flexivel
para UI, mas custa tempo quando milhares de agentes rodam por frame.

Otimizações seguras:
- Criar RuntimeConfig por frame/substep com valores ja resolvidos por especie.
- Criar uma versao/config_dirty nos Params. Sensores so atualizam retina_count,
  fov, radius e flags quando essa versao muda.
- Evitar strings como f'{prefix}_...' dentro de loop por agente.

Risco: baixo, se testes cobrirem alteracao de parametros em tempo real.


P1 - [FEITO/TESTADO] CollisionSystem tem overhead de pares
Status: indice por frame e query buffer implementados; raio de busca conceitual ainda nao alterado.

O custo atual de colisao no substrato real foi 0.919 s em 120 steps. Nao e o
maior gargalo, mas ainda pesa. O sistema usa:
- query_ball por agente
- tuple(sorted((id(agent), id(other)))) para deduplicar pares
- set de pares processados

Otimizações seguras:
- Atribuir indice inteiro estavel por frame para agentes e processar apenas
  pares other_index > agent_index.
- Evitar tuple(sorted(...)) em loop quente.
- Usar buckets de agentes apenas, sem comidas.
- Avaliar se colisao agente-agente precisa rodar todo frame para todos, ou se
  pode ser faseada sem mudar muito a dinamica. Esta ultima e opcional, pois pode
  alterar a fisica.

Alerta conceitual:
- A query de colisao usa agent.r * 2.0. Em corpos de raios diferentes, isso pode
  ser insuficiente para encontrar pares quando o outro e maior. Corrigir isso
  pode mudar a simulacao por tornar colisões mais corretas. Deve ser tratado
  como correcao com benchmark, nao como micro-otimizacao silenciosa.

P2 - [NAO FEITO NESTE LOTE] Threading/render/simulacao
Status: importante para UX, nao necessariamente para throughput.

Hoje o loop visual chama engine.step e render no mesmo fluxo. Se step demora,
a UI congela. Se render demora, a simulacao tambem atrasa.

Opcoes:
- Simulacao em thread propria com timestep fixo e buffer de estado para render.
- Render sempre mostra ultimo snapshot disponivel.
- Se a simulacao atrasar, render pula frames em vez de empilhar trabalho.

Risco:
- Medio/alto. Concorrencia pode criar bugs de estado.

Ordem recomendada:
1. Primeiro medir render.
2. Depois aplicar culling/simple render.
3. So entao considerar double buffering.
